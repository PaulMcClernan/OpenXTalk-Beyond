- Android: the packages the builder makes install again. Test builds and "Sign for development only" builds are signed with the Android SDK's debug key (made with the JDK's keytool when it is missing, as Android Studio makes it), as LiveCode's builder signed them; before, they were not signed at all. "Sign with my key" builds are aligned before they are signed, so they keep the v2 and v3 signatures that Android 11 and newer need for an app that targets API 30 or newer (before, zipalign took them off again and apksigner refused the package), and the signature is checked once it is made. The keystore passwords reach apksigner through the environment, no longer on its command line, and the old SHA-1 jarsigner fallback is gone. On Windows, a keystore chosen in the Android settings is found (its C:/ path was taken for a relative one) (#353)
- Android: the builder puts the package together with revZip and lists the compiled classes itself, instead of running zip, sh and find, which Windows does not have (#353)
- Android: an app with a push sender ID installs on Android 12 and newer: its push receiver says android:exported="true", the value older Androids gave it (#353)
- Android: the builder warns, without changing the package, when it has armv7 code without arm64 (or x86 without x86_64), which Google Play refuses; when an extension has native code for some of the chosen architectures and not others; and when an extension's manifest adds an activity, service or receiver with an intent-filter and no android:exported, which Android 12 and newer refuse to install (#353)
- Android: the SDK's d8 and apksigner run with the JDK chosen in Preferences, also when JAVA_HOME names an older Java. They are scripts that take JAVA_HOME's java before the PATH's, so a JAVA_HOME left at Java 8 (as on GitHub's Windows runners) made every build fail with "could not encode class bundle: ... UnsupportedClassVersionError". The JDK of Preferences takes JAVA_HOME's place while they run only when it is at least as new, so neither script gets an older Java than before; an unset JAVA_HOME stays unset (#353)
- Android standalone settings: a stack with Android on and no architecture saved gets arm64 ticked beside armv7 when its Android card opens. A stack that never opened the card still builds for armv7 alone (#353)
- Android SDK: a build with an SDK that lacks something says what it lacks and how to install it, instead of only "not a valid Android SDK". An SDK with no Android 13 (API 33) platform but a newer one is taken, with the lowest newer platform; the SDK needs apksigner, which every build-tools release with d8 (which the builder already needed) has (#353)
- CI: the workflow "Android builder" builds Android packages with a released IDE's builder and with this one, from the same probe stack, on Windows, Linux and macOS with the runner's Android SDK, checks them (signatures, zipalign, resources.arsc, android:exported, 16 KB pages), compares the two builders' packages file by file, and on Linux runs the IDE's Test and the packages on an Android 13 emulator and on one with 16 KB pages (tools/ci/android_check.py, tools/ci/android-check.livecodescript) (#353)
