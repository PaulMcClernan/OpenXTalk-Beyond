- Android standalone builder: a stack can ask for an Android App Bundle (.aab), which Google Play takes for a new app, beside its package, with its "android,app bundle" standalone setting. The bundle holds what the package holds, keeps the native libraries compressed and the stack's files stored in the device's packages (so the app loads its externals and reads its files as before), and is signed with the package's key; the builder warns when it is signed with the debug key or not signed, which Google Play refuses. The first such build downloads Google's bundletool 1.18.3 (checked by its SHA-256) into the IDE's cache folder, or uses the jar that the cMobileSupport["android.bundletool"] of stack "revPreferences" names; it needs aapt2 from the SDK's build-tools. Packages are made as before, and a stack without the setting gets no bundle (#397)
- Android builder check: the builds include a bundle build, whose App Bundle android_check.py verify checks (the package's files with the same bytes, native libraries compressed and assets stored, the package's signer, bundletool reading it, the target API, the bundletool the builder pins; --jdk for jarsigner, keytool and java), and device installs an App Bundle as Google Play does (bundletool's split APKs for the device; --bundletool, --jdk). The Java layer's probe carries a file and reads it on the device. The workflow runs the App Bundles on the Android 13 emulator, and the Java layer's probe's on the 16 KB image at API 36 too. device starts a package once the system has taken its install (its broadcasts delivered, the package manager idle), as Android 16 killed the Java layer's probe for memory while its apps were still taking it (#397)
