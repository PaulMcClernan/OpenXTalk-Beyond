Naming a job

So far every example has been a list of lines that run once, top to bottom. As soon as a program does the same job twice, you want to give the job a name and write its lines once. In xTalk a named job is a handler, and the simplest kind is a command.

A command handler starts with on and its name, and ends with end and the same name. To run it, write its name as a line of its own, just like put or add:

Writing the handler does nothing by itself; it only teaches xTalk a new word. The lines run each time something calls it, here twice.

The playground lets you write handlers and the lines that call them side by side, so that you can try them quickly. In an object's script every line lives inside some handler: the calls would go in a mouseUp handler, or in another command of your own.

Handing it values: parameters

A command becomes far more useful when you can tell it what to work on. List names after the handler's name, separated by commas: these are its parameters. When you call it, put the values after the command's name in the same order, and each parameter holds one of them while the handler runs.

A parameter you leave out is simply empty, so a handler can give it a sensible value of its own, as greet does. Many xTalk programmers start parameter names with p, so that you can tell at a glance which values came in from outside.

Any number of values

A handler can also take as many values as you care to give it. the paramCount says how many came, and param(n) gives the n-th one, whether or not it has a name.

Getting an answer back

A command can report back with return. The value does not appear where you called it; it goes into the result, which you read on the very next line, before anything else changes it. The usual habit is to return empty when all went well and a message when something did not:

Parameters are copies

A parameter holds a copy of the value you passed. Changing it inside the handler does not change the variable you called it with:

That is almost always what you want: a handler cannot spoil your variables by accident. When you really do want a handler to change one, put @ before the parameter's name. The parameter then is the caller's variable, not a copy:

Use @ sparingly. A function that returns a new value (the next lesson) is usually clearer, because the line that calls it shows where the value goes.
