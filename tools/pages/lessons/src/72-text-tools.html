What changed: Diff

Two versions of a text, a note before and after someone edited it, look alike but differ somewhere. The Diff library finds where. DiffCompare takes the old text, the new text and how many unchanged lines of context to show around each change, and gives back a diff: a line starting with - was taken out, one starting with + was put in, and one starting with a space is context, unchanged:

This is the unified diff format that programmers' tools such as git use, so a diff made here can be read there. The @@ line says where the change sits: lines 1 to 3 of the old text became lines 1 to 4 of the new one. Each line here ends with a return, as the lines of a text file do; a last line without one is told apart with a line \ No newline at end of file, so it shows as changed when a line is added after it. The diff's own lines end with a return too, and line 1 to -1 of leaves off the last one, so the Message Box shows no empty line after it.

A diff is also a recipe. DiffPatch applies one to the old text and gives the new text, so a program can keep the first version and the small diffs after it, rather than every version whole:

Two texts that are the same give an empty diff, which is a quick way to ask "did anything change?". DiffCompareFiles does the same as DiffCompare with two file paths, reading the files for you.

Because every changed line starts with its sign, a script can count the changes, or show them in colour:

A changed line counts as one taken out and one put in, which is how diffs see the world: two did not become 2, it was removed and 2 was added in its place.

A command line's options: GetOpt

A program run from a terminal is given its settings as options after its name: report -v --output=summary.txt notes.txt. Short options are a dash and a letter (-v), long ones two dashes and a word (--verbose), and what is left, here notes.txt, are the arguments. GetOpt sorts them out. Its first parameter, the grammar, lists the options it should know, separated by spaces, each with its other names before it after commas; a = at the end means that option takes a value:

The answer is an array of three: options, keyed by each option's last name in the grammar, however it was written; arguments, numbered; and errors. -o summary.txt, -osummary.txt and --output summary.txt all mean the same, and short options can share one dash: -hv is -h -v.

A real program leaves out the second parameter, and GetOpt reads the commandArguments, the words the program was started with. Anything it cannot make sense of goes into errors, a message each, so a program can say what is wrong and stop:

A -- on its own ends the options: everything after it is an argument, even a file that happens to be called --help. That is the same rule every Unix tool follows, so people who use terminals will expect it.

File types and email: MIME

The MIME library, met in Using extensions, knows the MIME type of each kind of file, the label a web server or an email gives it. It also works the other way, from a type to the file endings that have it:

An email can carry only plain letters, digits and a few signs, so anything else is encoded first. mimeEncodeForMIMETransfer does both of email's encodings: quoted-printable, which leaves plain letters alone and writes the rest as = and two hex digits, and base64, which turns any bytes into letters. Text is encoded as UTF-8 first:

mimeEncodeAsMIMEEmail builds a whole email, headers, body and attachments, and puts it in it, ready to hand to a mail server. Each attachment is an element of an array, with its name and its data (or a filepath), and its type comes from its name:

Sending it is another job, for a mail server and its password; the IDE's tsNet library can do it, as the Dictionary's page for mimeEncodeAsMIMEEmail shows. Never put a mail password in a stack you give away.
