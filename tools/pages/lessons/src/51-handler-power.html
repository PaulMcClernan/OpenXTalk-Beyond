Changing the caller's variable: @

A parameter is normally a copy: changing it changes nothing outside the handler. Put @ before its name and the parameter is the caller's variable, passed by reference, so the handler can change it. By custom such a parameter's name begins with r:

By reference is also quicker for big values: a large array passed with @ is not copied. Use it for that, or when changing the caller's variable is the whole point, as with addItem; otherwise a function that returns a new value is easier to follow.

Reporting failure: return for error

xTalk's own commands report a problem in the result (Reading and writing files), and yours can too. return ... for error leaves the problem in the result, and the call's value empty; return ... for value gives back the answer and leaves the result empty. Read the result at once, or put it into a variable: the next command may change it. And give a function that can fail for value on its normal return too, because a plain return from a function also leaves its value in the result, where a check would take it for a problem.

Return for error suits problems the caller should expect and handle, such as a missing file or a bad value typed in. For a mistake that means the program itself is wrong, throw (Handling errors) is better: it cannot be ignored by accident.
