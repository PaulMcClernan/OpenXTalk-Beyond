From stack to program

A stack needs OXT-Beyond to open it. A standalone application does not: it is the engine and your stacks built into one program, which runs on a computer that has never seen OXT-Beyond. File > Save as Standalone Application builds one, into a folder for each platform you chose, next to the stack file.

Before the first build, open File > Standalone Application Settings. The settings are kept in the stack itself, so they are saved, and shared, with it:

  • General: the program's name, and its inclusions (below).
  • Stacks: the other stack files to build in, such as libraries and behaviors kept in files of their own.
  • Copy Files: files and folders that go beside the program: pictures, sounds, help pages, a starting database.
  • One pane for each platform: whether to build for it, and its icon, version and copyright.
  • Bug Reports: what the user sees when an error is not caught (below).

Build early and run the result on a clean computer, not only on yours. Most surprises in a standalone (a missing library, a file it cannot find, a folder it may not write to) show up in the first minute.

Inclusions: what the program needs

The engine alone has every xTalk command, but not the libraries and extensions the IDE loads as it starts: the internet library, database support and its drivers, JSON, the HTTP server, widgets, OXT-Beyond's own extensions. A standalone carries only those it is given. Search for required inclusions looks through your scripts and adds what they use. Select inclusions lets you tick them yourself, on the Inclusions pane.

The search reads the words in your scripts, so it cannot see a library used through do (Dynamic code) or a command whose name is built in a string. If a standalone says a handler cannot be found when the IDE ran it happily, a missing inclusion is the first thing to look for: tick it by hand. For a database, tick both Database and the driver, such as SQLite (Databases).

Where to keep the user's data

A program cannot save itself. Its main stack is built into the program file, and the folder it is installed in is usually read-only for the user. So anything that must outlast a run (settings, the user's work, a cache) goes in a file in one of the user's own folders (Reading and writing files). A small settings file can be a whole array, turned into bytes with arrayEncode (Split, combine and friends) and back with arrayDecode. A real program keeps it where each system expects: specialFolderPath("support") on Windows (the user's AppData folder) and macOS (Application Support), and a folder in .config in the home folder on Linux. Give the program a folder of its own there, made the first time it is needed. The user's own documents belong in specialFolderPath("documents"), or wherever they choose with ask file (Dialogs).

Errors out in the world

In the IDE an error that nothing catches opens the script editor at the line. In a standalone there is no script editor: the Bug Reports pane decides what the user sees. A program can also handle them itself: an uncaught error sends errorDialog, with the error's details, to the object whose script failed, and from there along the message path, so a handler in the main stack's script hears them all. Writing them to a log file gives you something to read when a user says "it went wrong":

Catching errors where they can happen, with try (Errors), is still better: there the script knows what it was doing and can carry on. errorDialog is the net under everything else.

Script-only stacks and version control

A stack file holds cards, controls, pictures and scripts in a binary format. A version control system such as git can keep it, but cannot show what changed in it or merge two people's changes. A script-only stack is a plain text file that holds a stack's script and nothing else: its first line names the stack, and the rest is the script (the engine ends the file with a line break), ready for git and any text editor. Libraries and behaviors (Libraries, Behaviors) suit it well, so a program can keep almost all its code in script-only stacks and only its windows in a binary stack:

List the script-only stacks in the main stack's stackFiles, a stack name and a path relative to the main stack's file on each line, and the engine finds each by its name the first time a script refers to it, opening the file then. The Stacks pane of the settings lists them too, to build into the standalone.

A .livecodescript file is opened as a stack, so its first line must stay script "name" with the stack's name in quotes. Edit it in the IDE's script editor or any text editor, and save it as UTF-8.

Programs without windows

A standalone can also be a tool for the terminal, or a job a server runs. Started with -ui, it runs with no windows at all. the commandArguments holds what followed the program's name on the command line, a numbered array; write ... to stdout prints, and to stderr prints errors apart from the output; and quit with a number ends it with that exit code, 0 for success. Try it yourself
