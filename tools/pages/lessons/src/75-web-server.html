One handler, many addresses

The web and the internet started a tiny server to have something to fetch from. A server of your own can do much more: show a page to a phone on the same Wi-Fi, give data to another program, or be a whole app that people use from a browser. httpdStart sends every request to one handler, with an array that says what was asked: its method (GET to read, POST to send), its resource (the address's path, such as /about), its parameters, headers and content. A switch on the path is a list of routes:

The page for a missing path still arrives, and the result has its status; it is read straight after the get, because the next command, even a put, clears it. The number with each answer is its status: 200 means "here it is", 404 "no such thing". Others worth knowing are 400 (the request makes no sense), 405 (not with that method), 303 (look over there, with a Location header) and 500 (the server went wrong; the library sends this itself if your handler stops with an error). httpdStop with no port stops every server this program started.

Saying what you send

A browser decides how to show what it gets from its Content-Type header: text/html is a page to lay out, text/plain is shown as it is, application/json is data. Give it as the fourth parameter of httpdResponse, a header a line, and give text as UTF-8 and say so, or accented letters arrive broken:

To see it in a real browser, start the server with a port of your choosing, such as httpdStart "serve", 8080, and launch url "http://localhost:8080/". A phone on the same network reaches it at your computer's own address on that network, such as http://192.168.1.20:8080/.

Anyone who can reach your computer over the network can reach the server too, so serve nothing private, and stop it when you are done. Your system's firewall may ask whether to let it be reached; say no unless other devices need it.

A JSON API

An API is a server for programs rather than people: it answers with data, usually JSON (JSON). The same path can do different things for each method: here GET /notes lists the notes, and POST /notes adds the one sent in its content:

201 means "made". The notes live in a global, so they last while the program runs and are gone when it quits; a real app keeps them in a file or a database (Databases).

Serving a folder of files

A web site is mostly files: pages, pictures, style sheets. A route that finds the file named by the path and sends it, with the type the MIME library gives for its ending, serves a whole folder. One rule matters more than any other: never send a file outside the folder. A request for /../../secret.txt climbs out of it, so refuse any path with .. in it:

The browser shows a page from /, so it is common to send index.html for it, as here. Check the path before anything else: a server that forgets is one of the oldest ways of being broken into.

Data from a form

An HTML form sends what was typed as parameters, which the library decodes into an array, for a GET in the address and for a POST from its content. The values arrive as UTF-8, so decode them, and when you put one back into a page, escape it, so that someone who types <script> cannot put code into your page:

The page that has the form needs only <form method="post" action="/hello"><input name="name"><button>Send</button></form>, served from another route.
