The road a message takes

A message does not stop at the object it was sent to. If that object has no handler for it, it travels along the message path, through every object that holds it, until a handler answers it or it reaches the engine:

  1. the control it was sent to (the target)
  2. the group the control is in, if it is in one
  3. the card
  4. the card's background groups
  5. the stack, then its main stack, if it is a substack
  6. libraries and back scripts the program has added (Libraries shows how)
  7. the engine, which does its default job for messages it knows, and nothing for the rest

The first handler on the way runs, and the message stops there. Every object on the path has a script of its own: the Object menu opens them (Object > Object Script for what is selected, Object > Card Script, Object > Stack Script).

  1. On a new card, drag a Standard Button and name it B. Leave its script empty.
  2. Put the first handler below in the stack's script (Object > Stack Script), and the second in the card's (Object > Card Script).
create button "B"
set the rect of it to 40,40,122,63

Click B in Run mode. The button has no script, so the message went to the card. The card had a handler, so the stack's handler, further along, never heard of the click. Click the card itself, away from the button, and the card's handler answers that click too.

Sending it on with pass

A handler that has done its part can let the message carry on with pass, and each object on the path gets its turn. To see every turn in the Message Box at once, these handlers add to what it shows with put ... after msg (msg is short for the Message Box) instead of replacing it:

  1. On a new card, drag a Standard Button and name it B.
  2. Put the three scripts below in the stack, the card and the button.
create button "B"
set the rect of it to 40,40,122,63

Inside each handler, me is the object whose script is running: first the button, then the card. the target stays the button all the way. Take pass mouseUp out of the card's script, click again, and the stack's line is gone.

A handler for a message the engine itself acts on, such as keyDown or closeStack, stops that action unless it passes the message. A keyDown handler without pass keyDown means the field never gets the key.

Groups on the path

A group sits between its controls and the card, so a group's script can serve every control inside it. That is a neat way to build a panel of buttons that share one handler:

  1. On a new card, drag three Standard Buttons into a column, about 160 points wide, and name them Small, Medium and Large.
  2. Select all three (drag a rectangle around them in Edit mode, or click each with Shift held) and choose Object > Group Selected.
  3. With the group selected, name it Sizes in the Property Inspector, and open its script with Object > Object Script.
create group "Sizes"
repeat for each item tSize in "Small,Medium,Large"
   add 1 to tCount
   create button tSize in group "Sizes"
   set the rect of it to 60, tCount * 50, 220, tCount * 50 + 36
end repeat

Clicking a grouped control in Edit mode selects the whole group. To change one of its buttons, choose Object > Edit Group first, or turn on Edit > Select Grouped Controls.

Where should a handler go?

  • In the control, when it is about that control alone: what this button does when clicked.
  • In a group, for controls that work together, like a set of tool buttons.
  • In the card, for what belongs to one screen: getting it ready in openCard (Cards and going between them).
  • In the stack, for anything the whole program needs: helper functions, saving, starting up.

The message path is one of HyperCard's big ideas, and it has hardly changed since 1987: button, card, background, stack, Home. In OXT-Beyond a HyperCard background becomes a group shared by several cards, and keeps its place on the path.
