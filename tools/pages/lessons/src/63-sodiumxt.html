libsodium, from xTalk

SodiumXT brings libsodium, the cryptography library that thousands of programs trust, to xTalk. Its handlers begin with sx, and each does one job the safe way, with modern methods chosen for you: you never pick an algorithm, a mode or a padding, which is where most home-made cryptography goes wrong. Hashes, randomness and encryption met two of them; this lesson takes the whole tour.

Everything here works on bytes, not text. textEncode(tText, "UTF-8") turns text into bytes before it is locked, and textDecode turns them back after (Unicode). Keys, fingerprints and locked boxes are bytes too, which look like gibberish when you put them, so the examples show them as hex or base64:

Hex takes two letters a byte and is easy to read; base64 takes four letters for three bytes, so it is shorter. Both survive an email, a field or a web form, which raw bytes may not.

Random bytes nobody can predict

Every key starts as random bytes, and they must come from the computer's secure source, never from random, whose numbers follow a pattern. sxRandomBytes gives as many as you ask for, and sxRandomUniform(n) a fair whole number from 0 to n - 1, a die with any number of sides:

The first two lines differ every run, which is the point.

Fingerprints and seals

A hash is a fingerprint of data: always the same size, always the same for the same data, completely different for the smallest change, and impossible to work back from. sxHash makes a BLAKE2b fingerprint of the length you ask for (32 bytes is usual), and sxSha3_256 a SHA-3 one:

Anyone can make a plain fingerprint, so a changed message can come with a changed fingerprint. A seal (a keyed hash) needs a secret key as well: only someone with the key can make one that matches. sxHashKeyed makes a BLAKE2b seal and sxHmacSha256 the HMAC-SHA256 seal that many web services ask for. Compare seals with sxMemEqual, never with is: it takes as long however much of them matches, so its timing gives nothing away:

Secret boxes

A secret box locks a message with a key of 32 random bytes. With the key, sxSecretBoxOpen opens it; without it, the box is noise. It also notices tampering: change one byte, and it refuses to open, with an error you catch with try (Errors), rather than hand back nonsense:

The box is 40 bytes longer than the message: a random nonce, so that the same message locked twice looks different each time, and a tag that proves it is untouched. SodiumXT makes the nonce and keeps it in the box, so there is nothing for you to get wrong.

Sometimes part of a message must stay readable, like the address on an envelope, but nobody may swap it. sxAeadEncrypt locks a message and ties a readable label to it; sxAeadDecrypt opens it only with the very same label, so nobody can move a locked box to another record:

Public keys

With a secret box, both people need the same key, and handing it over safely is the hard part. With public-key cryptography each person makes a keypair: a public key to give to anyone, and a secret key to keep. sxBoxKeypair makes one, putting the two keys into the variables you give it, which must be declared first with local (Scope): a name that is not yet a variable is passed as the text of its name. sxBox locks a message for one person, with your secret key and their public key, and sxBoxOpen opens it and proves who sent it. sxSeal needs only the reader's public key: like a postbox, anyone can post and only the owner can open:

Signatures

A signature hides nothing: it proves who wrote something, and that nobody has changed it since. You sign with your secret key, and anyone with your public key can check. Software updates, licences and Nostr posts are signed this way:

Agreeing on keys in the open

Public-key boxes are slow for a long conversation. With a key exchange, two programs each mix their own keypair with the other's public key, and both get the same pair of fast secret keys without ever sending them: one to send with and one to receive with. Files and streams

A big file need not fit in memory. sxEncryptFile and sxDecryptFile lock and unlock a file of any size a piece at a time, so its bytes never pass through your variables, and the locked file notices tampering as a box does. sxHashFile fingerprints a whole file, to check a copy or a download:

Data from a network or a recording arrives in pieces. A secret stream locks each piece with one key, in order, and marks the last; the reader opens them in the same order and notices a piece that is missing, swapped, repeated or cut short. sxSecretStreamInitPush starts one and gives a header to send first, sxSecretStreamPush locks a piece (true for the last), sxSecretStreamPull opens one, and sxFreeStream lets the stream go:

Many keys from one, and lengths that tell less

sxKdfDerive makes many keys from one master key: give it the master, a number and a label of exactly 8 bytes, and each number gives an unrelated key, none of which gives the master away. One key for files, another for messages, and only the master to keep safe. A locked message still shows its length, and "yes" and "no thanks" are easy to tell apart by size alone, so sxPad grows data to a whole number of blocks and sxUnpad takes the padding off:

A key is only as safe as where you keep it. Never put one in a script, where anyone with the stack can read it; derive it from a password with sxPwHash (Storing passwords), or keep it in the system's own key store. The Dictionary has every SodiumXT handler, and the Learn SodiumXT stack (Help > Examples, under The xTalk Suite) has these ideas as scripts to change and run.

Try it yourself

Write encryptText and unencryptText: the first locks text with a key and returns it as base64, safe to keep in a field or a file; the second takes that base64 back to the text, or returns empty when the key is wrong or the text was changed.
