charToNum and numToChar come from the days of one byte a character. They still work for plain English text, but use codepointToNum and numToCodepoint for anything else.

Characters, codepoints and code units

What a reader sees as one character can be more than one codepoint: an e followed by a combining accent is one character, é, made of two codepoints. And inside the engine some codepoints take two code units. Usually you want chars; the others are there when you need them:

Comparing accented text

The same word can be stored in two ways: with é as one codepoint, or as e plus an accent. They look identical, and xTalk treats them as the same, as it ignores case: is, offset and array keys all see one word. But their bytes differ, so once the text leaves xTalk, written to a file, hashed or sent to a server, they are two different words. Set the formSensitive to true to compare the forms exactly, and use normalizeText to put text into one standard form, NFC:

Text typed on a Mac and text from a web form can arrive in different forms. Normalize text from outside before you save it, hash it or send it on, so the same word always becomes the same bytes.

Text and bytes: encodings

Files and networks carry bytes, not characters. An encoding is the rule that turns one into the other, and today's standard is UTF-8, which uses one byte for plain English letters and two to four for the rest. textEncode turns text into bytes, and textDecode turns bytes back into text:

The rule to remember: decode as text comes in, encode as it goes out. Read a file's bytes and textDecode them; textEncode text before you write it to a file or send it. The next lessons, Reading and writing files and Files a piece at a time, do exactly that.
