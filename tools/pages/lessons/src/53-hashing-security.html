Fingerprints: hashes

A hash turns any amount of data into a short fingerprint of fixed size. The same data always gives the same hash, and the smallest change gives a completely different one, so a hash tells you whether a file arrived intact or has changed since you last saw it. messageDigest makes one with the algorithm you name; the result is bytes, best shown in hexadecimal (Binary data):

Hash text by its UTF-8 bytes, as here, so the same text gives the same hash on every system. "SHA-256", "SHA-512" and "SHA3-256" are good choices today.

md5Digest and sha1Digest are still there for old formats that need them. Both are broken for security: people can make two different files with the same MD5 or SHA-1 hash. Use them to match an old checksum, never to protect anything.

Signing a message: HMAC

A hash shows that data changed, but anyone can compute one, so an attacker who changes a message can change its hash too. An HMAC mixes a secret key into the hash: only someone with the key can make the right code, so a message that arrives with a matching code came from someone who knows the key, unchanged. Random enough to be secret

random is fine for games, but its numbers can be predicted, which makes them useless for anything secret. randomBytes takes bytes from the system's secure source, the right way to make a key, a token or a salt. uuid makes a unique ID, 36 characters, safe to use as the name of a record or a file without asking a server for one:

Storing passwords

Never store a password, and never store a plain hash of one: computers can try billions of guesses at a SHA-256 hash every second. A password needs a hash made to be slow and to use a lot of memory, with a random salt so that two people with the same password get different hashes. OXT-Beyond comes with libsodium, through the SodiumXT extension, whose sxPwHashStr does all of this with Argon2id and gives back one line of text to store. sxPwHashStrVerify checks a password typed at login against it:

Hashing the same password twice gives two different lines, because each has its own salt, and both still match. The line records the salt and the settings, so it is all you store.

Encrypting

To keep data secret but get it back later, encrypt it with a key. libsodium's sxSecretBox encrypts and also seals the data, so any change to it, or the wrong key, is refused rather than giving nonsense:

The key is 32 random bytes. Keep it as safe as the data: anyone who has it can open the box. To make a key from a password instead, see sxPwHash in the Dictionary.

Encryption is easy to get subtly wrong. Use these ready-made, complete tools as they are, keep keys out of your scripts (a key written in a stack can be read by anyone who has the stack), and do not invent your own scheme.
