Everything is a message

When the user does something, xTalk tells the object it happened to by sending it a message: a word such as mouseUp, keyDown or openCard. If the object's script has a handler with that name, the handler runs. If not, nothing visible happens, and the message moves on (the next lesson follows where it goes).

This is the heart of every xTalk program: you do not write a main loop that waits for clicks. You write small handlers, put each in the object it belongs to, and xTalk calls them at the right moment.

A button with a script

You have already written one handler: the button in Stacks, cards and controls. Here is the smallest one there is.

  1. On a new card, drag a Standard Button and name it Hello.
  2. Open its script (Object > Object Script) and type the handler below, then press Apply.
create button "Hello"
set the rect of it to 40,40,122,63

In Run mode, the click sends mouseUp to the button, and its handler runs. A script, or you in the Message Box, can send a message to an object just as a click would, and read an object's script, which is a property like any other:

A script can even set the script of another object, which is how the examples of the playground make buttons that do something. You will rarely need to: type scripts in the Script Editor, where they are coloured and checked as you go.

Messages that carry a value

Some messages come with information, which arrives in the handler's parameters: mouseUp says which mouse button was used (1 is the main one), and keyDown which key was typed.

  1. On a new card, drag a Standard Button and name it B.
  2. Drag a Field under it and name it Typing.
create button "B"
set the rect of it to 40,40,122,63
create field "Typing"
set the rect of it to 40,80,240,101

Now give the field this script. In Run mode, click into the field and type: each key shows in the Message Box, and pass keyDown lets it on into the field. To try it without typing, send the field a keyDown from the Message Box:

A keyDown handler that does not pass the message swallows the key, so the field never shows it. That is how you stop a field taking letters when only digits make sense: handle keyDown, and pass keyDown only when the key is a digit.

One handler, many controls

A control with no handler for a message lets it go on to its card and then its stack (The message path follows it all the way). So a handler in the card's script hears the clicks of every button that does not handle them itself, and the target says which one it was:

  1. On a new card, drag two Standard Buttons side by side, and make each about 140 points wide and 50 high. Name them Left and Right.
  2. In the Property Inspector's Basic section, set the Label of each to 0. Leave the buttons' scripts empty.
  3. Open the card's script with Object > Card Script.
create button "Left"
set the rect of it to 60,60,200,110
set the label of it to 0
create button "Right"
set the rect of it to 220,60,360,110
set the label of it to 0

Click Left three times and Right once, and the Message Box counts along. The if leaves the card's own label alone when you click the card between the buttons.

Messages when a card opens

Going to a card sends it openCard. It is the place for a card to get ready: fill its fields, start a timer, reset a game.

  1. In your stack, choose Object > New Card, and name the new card Second in the Card Inspector (Object > Card Inspector).
  2. Open its script with Object > Card Script.
create card "Second"
go to card 1

Now go back and forth with View > Go Prev and View > Go Next, or in the Message Box:

Two lines: only arriving at Second sends the message to its script. A handler in the stack's script (Object > Stack Script) would hear every card open, since a card with no openCard handler passes the message on to its stack.

Send and dispatch

send delivers a message as if xTalk had sent it. If no handler anywhere answers it, send stops with an error. On a card with a button B that has no script:

  1. Drag a Standard Button onto a card and name it B. Leave its script empty.
create button "B"
set the rect of it to 40,40,122,63

dispatch is the polite form: it delivers the message if someone handles it, and either way sets it to handled or unhandled, so your script can tell. Give the card a tidyUp handler of your own (a command: the lesson Commands explains them), and a button that dispatches it and a message nothing handles:

  1. Drag a Standard Button onto a card and name it B.
  2. Put the first script below in the card's script (Object > Card Script), and the second in the button's.
create button "B"
set the rect of it to 40,40,122,63

Nothing answers refresh, and that is fine. tidyUp goes from the button on to the card, whose handler runs (its put is replaced in the Message Box by the last one).

Use dispatch when you tell objects about something they may or may not care about ("the score changed"). Each object that wants to know has a handler; the others are left alone.

Try it yourself

On a new card, drag a Field named Log and three Standard Buttons named Apple, Pear and Plum. Write one mouseUp handler, in the card's script, that adds the name of the button clicked as a new line of the field, and puts which line it is. Then click Pear, Plum and Apple.

  1. Drag three Standard Buttons in a row, about 120 points wide, and name them Apple, Pear and Plum.
  2. Drag a Field below them, make it big, and name it Log.
create field "Log"
set the rect of it to 40,90,440,200
repeat for each item tFruit in "Apple,Pear,Plum"
   add 1 to tCount
   create button tFruit
   set the rect of it to tCount * 140 - 100, 30, tCount * 140 + 20, 70
end repeat
