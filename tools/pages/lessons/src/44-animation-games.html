Moving a control: move

The examples in this lesson make their controls with create (Making controls from a script), so that each one runs in the playground in one piece. In a stack of your own you would drag the same controls from the Tools palette, name them in the Property Inspector, and put the handlers into their scripts: the code works the same either way.

The simplest animation is one command. move slides a control to a point over a time you give, and the engine draws every step between. Give it a list of points, such as a graphic's points, and it follows them one after another:

move waits until the control arrives. Add without waiting and the script goes on at once while the control moves; the movingControls lists the controls still on their way:

Frame by frame

For anything move cannot do (a ball that bounces, a game where everything moves at once) animate it yourself: a handler that changes positions a little, then sends itself again a moment later, as in Timers and waiting. Each run is one frame. About 16 milliseconds between frames gives 60 a second, as smooth as most screens show.

Three habits in this example are worth keeping:

  • Keep the long id. After create, it is the new control's long id (Referring to objects). Kept in a script local, it finds the control from any handler, whichever stack is in front when the timer fires. A name such as graphic "Ball" is looked for on the card in front, which, when a timer fires, may be another window's.
  • Measure from me. the width of me is the width of the card or stack whose script this is, which is the same whichever window is in front.
  • Lock the screen. lock screen (Making code fast) holds what is drawn until unlock screen, so the ball's two moves and the trail's new point appear together, as one frame, never half done.

The arrow keys

A key pressed while no field is being typed in goes to the card as a message: arrowKey for an arrow key, with left, right, up or down, and keyDown for any other, with the character. A player moved by the keys is a pair of handlers. Here, send presses the keys, so the example runs by itself:

An arrowKey handler that does not pass the message stops the arrow keys doing what they normally do, such as moving to the next card. That is usually what a game wants.

Collisions

intersect tells whether two controls overlap. Their rectangles are compared, unless you ask for "opaque pixels", which compares what is actually drawn: slower, but exact for round or odd shapes.

A small game

Put the pieces together: a basket at the bottom of the stage, coins that fall from the top, and a point for every coin the basket catches. Each frame moves every coin down, checks each for a catch, and starts a fallen one again at the top. Here the basket heads for the lowest coin by itself, so the example plays itself; in a real game the arrow keys would move it. randomSeed makes random give the same numbers each run, which is how a game can replay a level:

A real game adds a few things to this shape: arrowKey handlers to move the basket, a frame count or time limit for each level, and a closeCard that cancels the timer (Timers and waiting) so the game stops when its card closes.
