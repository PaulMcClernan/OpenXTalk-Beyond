Every programmer debugs

A bug is a difference between what you meant and what you wrote. Finding one is not a sign you are bad at programming: it is most of programming. The trick is to stop guessing and start looking. This lesson is a toolbox for looking.

1. Read the error

When a script stops, xTalk tells you where and why. The playground highlights the line and explains in plain words; the Script Editor shows the error under the script and puts its line in view. Read the whole message: it usually names the problem exactly.

Here, line 3 divides by zero, because there are exactly three items. The message says so, and the line number says where.

The line an error is reported on is where the trouble showed, which is not always where it started. If a value is wrong on line 30, the question is which earlier line made it wrong.

3. Stop and look around: the debugger

Click in the Script Editor's left margin, next to a line, to set a breakpoint: a red dot. When the script reaches that line it pauses, and the Script Editor becomes the debugger. Now you can:

  • see every variable of the handler and its value, in the Variables pane at the bottom;
  • Step Into the next line (and into any handler it calls), Step Over it, or Step Out of the handler;
  • look at the stack trace: which handler called this one, and which called that;
  • Run on to the next breakpoint, or Stop.

A script can set a breakpoint too, with the command breakpoint, handy for pausing only in an unusual case:

Breakpoints pause only in the IDE, and only while Script Debug Mode is on (in the Development menu). A standalone application ignores them.

4. Test in small pieces

A long handler that does everything is hard to debug, because a wrong answer could come from anywhere in it. Split the work into small functions, and check each with a few values whose answers you know. When one fails, you know exactly where to look:

5. The usual suspects

Most bugs in xTalk are one of a handful. Check these first:

  • A misspelled variable, which xTalk reads as its own name, as text. Turn on Variable Checking (Edit > Options > Variable Checking in the Script Editor) and these become errors (Where variables live).
  • A misspelled property, which silently becomes a custom property (Properties).
  • The wrong order of operations, as above: add brackets.
  • A trailing return or space in a value, which makes is say false: compare the length of the two values.
  • A message that never arrives: a handler further along the message path caught it and did not pass it.
  • The wrong itemDelimiter (Chunks), left set to something else by earlier code.
