When something goes wrong

Some mistakes are found before a script runs: a misspelled end if, a missing quote. Others only show up as it runs: a division by zero, a number that turns out to be a word, a file that is not there. These runtime errors stop the handler, and every handler that called it, and xTalk reports where it happened.

That is the right thing while you are writing a program. In a finished one, you would rather the program noticed the problem and dealt with it.

Catching errors: try and catch

Put the lines that might fail between try and catch. If any of them raises an error, xTalk jumps straight to the lines after catch, and the program carries on after end try:

The variable after catch receives a description of the error. For xTalk's own errors, each line of it is a set of numbers: the first item of the first line is the error's code, the second the line it happened on.

Raising your own: throw

throw raises an error of your own, with any text you like. It travels up through the handlers that called it, just like one of xTalk's, until a try catches it, and then the text arrives in the catch variable exactly as thrown:

The third check never ran: the error jumped straight to catch. An error can travel a long way up:

Throw where you find the problem, catch where you can do something about it, often far apart. The handler that reads a file knows it is damaged; only the handler that started the program knows to show a message and use the defaults.

Tidying up: finally

Lines after finally run whether or not there was an error: the place to close a file, unlock the screen, or put the cursor back.

Errors that do not throw

Not every problem raises an error. Commands that deal with the world outside, files, the internet, other programs, often report a problem by setting the result (Your own commands) and carrying on. A try would not notice; you must look:

So after any command that reaches outside your program, check the result on the very next line, before another command replaces it.

An error nobody catches reaches the engine, which sends the message errorDialog; in a standalone application with no handler for it, the user sees the engine's error dialog. A stack can handle errorDialog to log errors its own way.

Try it yourself

Write a function toNumber that gives back its parameter if it is a number, and throws not a number: followed by the parameter if not. Then add up the list 4,x,10,oops,6 with it, skipping anything that is not a number and putting a warning for each.
