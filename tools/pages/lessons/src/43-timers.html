Waiting

wait pauses the handler for a time, in seconds, milliseconds or ticks (sixtieths of a second):

While a plain wait lasts, the whole program waits with it: a click is not answered, and a timer does not fire. That is fine for a moment's pause, but not for anything longer. wait ... with messages lets the rest of the program carry on during the wait, and wait until waits for a condition to become true:

A wait until without with messages waits forever for a condition that only a message could change: nothing can run to change it.

Later: send in

Usually you do not want to wait at all: you want something to happen later while the program goes on. send (Messages and events) with in and a time does exactly that. It sets a timer and returns at once; when the time comes, the message arrives like any other:

The message is text, so the values for its parameters go after its name, as you would type them: here 3. To pass a value from a variable, join it in: send "ring" && tCount to me in 1 second.

Again and again

A handler that sets a timer for itself runs again and again: this is how a clock ticks, a game moves, or a program checks for new mail. Give it a way to stop, or it goes on until the stack closes:

Unlike a repeat loop, a handler that sends itself lets everything else happen between its runs: clicks are answered, fields can be typed in, and other timers fire. It is the right shape for anything that goes on over time.

Keep what a timer handler needs in script locals, as sCount here: a handler's own variables are gone when it ends, and the next run starts again with none.
