One script, many objects

A game has twenty enemies; a form has a dozen fields that check what is typed; a toolbar has eight buttons that light up under the pointer. Copying the same script into each works until you find a bug in it, and must fix it twenty times.

A behavior is the answer. It is an object (usually a button, or a script-only stack) whose script works for every object whose behavior property is set to it. Change the behavior's script, and every object that uses it changes at once.

A first behavior

The examples in this lesson make their controls with create (Making controls from a script), so that each one runs in the playground in one piece. In a stack of your own you would drag the same controls from the Tools palette, name them in the Property Inspector, and put the handlers into their scripts: the code works the same either way.

In a stack you would type the behavior's script into a button with the Script Editor and hide the button. So that the example runs by itself, it sets the script from text, a line at a time:

Three things to notice:

  • Inside a behavior, me is the object using it, not the behavior's button. The one script sets each button's own label.
  • Each object has its own script locals. sClicks counts each button's clicks apart: Tally 1's two clicks did not touch Tally 3's count. (sClicks + 0 shows a count still empty as 0.)
  • The buttons' own scripts are empty. A message that finds no handler in an object goes on to its behavior, before anything further along the message path.

Behaviors of behaviors

A behavior can have a behavior of its own, which makes a chain: from the most particular to the most general. A message goes along the chain until a handler takes it. Here the general behavior knows how to shout a description, and the particular one says what the description is. Behaviors in script-only stacks

In a real project, behaviors usually live in script-only stacks: stacks with nothing but a script, saved as plain text files (.livecodescript) that version control can compare line by line (Shipping your program shows how a program finds them). A program opens its behavior stacks before the objects that use them: list them in the stack's stackFiles, or start using them as libraries, which the next lesson explains.

Cards and stacks can have behaviors too. A card behavior is a good home for what every card of a kind does when it opens: set the behavior of each card to one script, and its openCard handler runs for each.

Try it yourself

Show a solution

The solution keeps each button's state in a script local, sOn, rather than reading its hilite back: a real click lights a button up while it is pressed and turns it off again as the mouse comes up, so the hilite says nothing about the toggle by the time mouseUp arrives.
